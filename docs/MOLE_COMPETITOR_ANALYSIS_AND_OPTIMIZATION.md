# Mole 竞品分析与 Memento 优化建议

> 分析日期：2026-08-04
>
> Memento 基线：`v0.6.60` / `7bec52e`
>
> Mole 基线：`V1.49.2` / `ad82a47b157c289a0feb52a414d4515a83ea7aaf`

## 1. 执行摘要

Memento 不应该把目标设为“做一个功能更多的 Mole”。Mole 已经在终端清理工具、规则覆盖、低门槛安装和社区反馈上形成明显优势；逐项追赶它的 `clean`、`status`、`optimize` 和大量清理规则，会让 Memento 陷入高风险、低差异化的长期维护战。

更有胜算的定位是：

> **Memento 是一个本地、可解释、确认后执行的 Mac 维护 Agent。它先用确定性扫描建立证据，再让用户理解、选择和验证操作；AI 是解释与编排层，不是扫描和清理的前置条件。**

建议立即做出五个产品决策：

1. **AI 可选，不做首次价值的门槛。** 没有模型时也要完整完成扫描、预览、批量选择、执行和历史审计。
2. **把“系统健康”和“可释放空间”拆开。** 未确认的残留线索不能扣健康分，也不能与安全可清理项混在一个数字里。
3. **先补可信清理闭环，再扩规则数量。** 统一预览、批量确认、操作历史、废纸篓恢复入口和执行后验证，比增加更多缓存目录更重要。
4. **公开发行先只承诺 macOS。** Windows/Linux 目前只是桌面壳验证，却以正式安装包形式发布，增加用户误解、CI 成本和支持面。
5. **避免与 Mole 正面复制。** 优先做完整卸载解释、启动项诊断、终端问题、磁盘目录归属和 Agent 证据关联；暂不追逐风扇控制、常驻监控、应用商店式更新管理等功能。

当前最紧急的问题不是功能缺失，而是信号质量。2026-08-04 在当前开发机执行 `npm run scan:smoke`，Memento 用时 `8.679s`，发现 108 个候选项，其中 97 个为存储项，78 个是“待确认”的隐藏目录线索。现有健康分公式会因为存储项数量直接降到最低值 45，即使大部分项目并不能证明是问题。这会损害用户对整个安全模型的信任，应作为 `0.7` 的第一修复目标。

## 3. Mole 的产品分析

### 3.1 产品结构

Mole 不是单一清理命令，而是一个清晰的双产品漏斗：

```text
免费开源 CLI
  -> Homebrew / curl 低门槛安装
  -> 社区提交真实 Mac 边界案例
  -> 高频修复和清理规则沉淀
  -> README、Release、博客持续导流
  -> $19 买断的专有原生 Mac App
```

免费 CLI 承担获客、口碑、规则验证和高级用户需求；原生 App 承担易用性与商业化。官网公开价格为 19 美元，一份许可证覆盖 2 台 Mac 并包含终身更新。README 还明确提供 14 天退款承诺，降低购买风险。

CLI 的核心任务被压缩为稳定、容易记忆的命令：

| 主任务 | 用户问题 | 产品价值 |
| --- | --- | --- |
| `clean` | 哪些缓存和残留可以清理 | 直接释放空间 |
| `uninstall` | 如何完整卸载应用 | 应用本体、启动项和精确残留一起审阅 |
| `optimize` | 哪些系统维护动作值得执行 | 把分散命令变成有边界的任务 |
| `analyze` | 空间到底被什么占用 | 可下钻的磁盘浏览和安全移到废纸篓 |
| `status` | Mac 为什么慢或热 | 实时指标和健康信号 |
| `purge` | 项目构建产物占了多少空间 | 面向开发者的高价值清理 |
| `installer` | 安装包是否长期堆积 | 聚合 DMG、PKG、ZIP 等文件 |
| `history` | 刚才删除了什么 | 可审计的操作记录 |

这套命令模型的优势是用户无需先理解技术架构，也不需要配置账号、模型或权限才能看到价值。

### 3.2 Mole 做得好的地方

#### 低摩擦分发

- `brew install mole` 是 Mac 技术用户最熟悉的安装路径。
- curl 安装作为兼容路径，安装器执行校验和验证并在验证失败时关闭失败。
- `mo` 无参数即进入交互菜单，也可以直接调用子命令。
- `--dry-run`、`--json`、自动检测管道输出和 NDJSON 让同一工具同时服务人和自动化。

#### 功能按真实任务组织

Mole 没有把大量规则直接展示成产品结构。用户先选择“清理、卸载、分析、状态”等任务，规则细节只在预览或结果中出现。这比按照扫描器内部模块组织 UI 更容易理解。

#### 清理规则来自真实兼容性反馈

近期 Issues 和 Release Notes 大量围绕 macOS 版本差异、运行中进程、同 Bundle ID 应用、EDR 缓存、Homebrew、Xcode、Corepack、Time Machine 和更新器边界。这说明 Mole 的壁垒不是一个扫描算法，而是持续积累的“哪些能碰、哪些必须跳过、何时需要重新确认”。

#### 清晰的安全预期

- 所有破坏性命令支持 dry-run。
- 集中路径校验和受保护路径规则。
- 清理白名单、应用保护、进程状态保护和超时边界。
- 操作日志与 `history --json`。
- 磁盘分析中的临时删除优先移到废纸篓。
- 高风险或无法确认状态时倾向跳过，而不是扩大匹配范围。

#### 社区与内容形成增长回路

仓库具备贡献指南、安全文档、Issue 模板、PR 模板、CodeQL、依赖更新和月度 Bundle 审计。官网同时维护多语言产品页、帮助中心、发布记录、博客、Markdown/LLM 索引和 Agent Skill。这些表面上不是“清理功能”，实际上持续降低发现、理解、购买和反馈成本。

### 3.3 Mole 的弱点与 Memento 的机会

#### Shell 规则规模带来长期复杂度

Mole 约 4 万行 Shell，需要同时处理 Bash 3.2、TTY、sudo、AppleScript、BSD 命令、超时、子进程和不同 macOS 行为。仓库契约中大量篇幅用于防止已经踩过的边界再次回归。Memento 的 TypeScript 类型、窄 IPC 和不透明操作 ID 更适合构建结构化 Agent，不应为了追求规则数量退回脚本堆叠。

#### dry-run 不等于可恢复

dry-run 能展示计划，但用户一旦执行永久缓存清理，通常没有统一撤销。Memento 可以把“预览、可恢复级别、执行后验证、废纸篓入口和历史记录”做成一套更完整的信任体验。

#### 复杂判断仍主要由用户承担

Mole 可以告诉用户路径、大小和类别，但对“这个目录属于谁、是否还在使用、为什么建议处理”主要依赖规则和用户知识。Memento 已有本机证据关联和模型解释能力，这是更有价值的差异点。

#### 功能面很宽

状态监控、优化、卸载、清理、磁盘分析和开发者工具同时维护，容易产生功能膨胀。Memento 应把 Mole 的广度当作选择压力，而不是待办清单。

#### 开源 CLI 与专有 App 是两个实现面

公开 CLI 的安全成熟度不能自动证明专有 App 使用完全相同的执行路径。Memento 可以用同一仓库、同一操作注册表和同一测试合同，把 UI、Agent 与执行器的关系做得更透明。

## 4. Mole 的技术分析

### 4.1 架构

Mole 采用 Shell 与 Go 混合架构：

```text
`mole` Shell 路由器
  +-- `bin/*.sh` 命令编排
  |     +-- `lib/clean/*` 清理规则
  |     +-- `lib/uninstall/*` 卸载规则
  |     +-- `lib/optimize/*` 维护任务
  |     `-- `lib/core/*` 安全、权限、日志、超时、UI
  |
  +-- Go `analyze` 二进制
  |     `-- Bubble Tea TUI、并发扫描、缓存、Spotlight、废纸篓
  |
  `-- Go `status` 二进制
        `-- gopsutil、系统指标、TUI、JSON/NDJSON
```

这个选择很务实：高变化的 macOS 清理知识保留在可快速迭代的 Shell 中，扫描和实时状态等性能敏感面使用 Go。代价是 Shell 安全合同和测试负担非常高。

### 4.2 值得借鉴的工程方法

#### 单一删除漏斗

`lib/core/file_ops.sh` 集中处理路径规范化、关键目录、符号链接、sudo、废纸篓、日志和 dry-run。业务规则不应各自实现删除。这与 Memento 的不透明操作注册表方向一致，但 Memento 还需要进一步统一直接清理、应用卸载、服务清理、磁盘删除和管理员操作的最后执行层。

#### 执行前再次检查

Mole 的规则反复检查运行进程、Bundle 身份、文件类型、路径归属和系统状态。扫描时成立不代表执行时仍成立。Memento 已经对操作 ID 和部分目标做二次校验，应将该模式提升为所有操作的统一前置条件合同。

#### 扫描性能分层

Go 分析器使用多类独立并发预算、Spotlight 补充大文件发现、硬链接去重、带 Schema 版本的持久缓存、过期策略和 stale-cache 首屏。缓存只用于展示和扫描加速，删除前仍重新验证目标。这比简单整卷等待后一次性展示更适合大磁盘。

#### 人机共用的数据接口

`analyze --json`、`status --json`、`status --watch` 和 `history --json` 让第三方工具、脚本和 coding agent 可以安全消费只读数据，而不必解析 TUI。这种稳定数据合同比开放通用 Shell 更值得 Memento 借鉴。

#### 测试围绕风险而不是文件数量

Mole 的测试重点覆盖危险路径、符号链接、同 Bundle ID、超时、TTY 恢复、sudo、安装校验、卸载残留、缓存一致性和 fuzz corpus。它的价值不只是测试数量，而是把每次真实故障转成长期约束。

### 4.3 不应直接照搬的实现

- 不应把 Mole 的 Shell 脚本嵌入 Electron 后直接调用。
- 不应复制其 GPL-3.0 代码、路径列表、应用保护表、测试夹具或规则表到 MIT 项目。
- 不应因为 Mole 使用 Go 就立即重写 Memento 扫描器。先测量瓶颈，再只下沉热点。
- 不应开放任意命令执行给模型来复刻 CLI 灵活性。
- 不应把大量系统优化动作标为“安全一键执行”，除非每个动作都有可解释前置条件、非目标清单和独立回归测试。

## 5. Memento 当前评估

### 5.1 已形成的优势

#### Agent 执行安全模型更适合长期差异化

Memento 的模型只看到精简扫描结果和不透明操作 ID，只能从当前扫描注册的操作中准备计划；用户确认后，主进程再次校验并执行，随后重新扫描验证。这个架构比让模型生成 Shell 命令更容易建立产品级信任。

#### Electron 权限边界明确

Renderer 没有数据库、API Key、原始文件目标或任意命令权限。Provider 创建、密钥解密、扫描、执行和持久化都在主进程，IPC 接口经过类型约束。

#### 本地数据与模型供应商设计完整

SQLite、WAL、AES-256-GCM、主进程密钥隔离、本机 AI 配置发现、真实连接校验和多供应商适配已经超过多数早期清理工具的基础设施成熟度。

#### 证据关联是有效差异点

Memento 会把存储、服务、应用、包收据、目录浅层内容和 Shell 引用关联起来，并区分本机确认、明确签名和未确认。这正好补足传统清理器只给路径和大小、不解释归属的弱点。

#### 发布链路已经具备商业软件基础

macOS 包使用 Developer ID 签名、公证和票据装订，并具备自动更新、跨架构构建和校验和清单。基础发布质量不是当前主要短板。

### 5.2 关键问题

#### P0：健康分语义失真

当前公式按存储候选数量每项扣 2 分，并把最低值限制为 45。实机扫描的 78 个未确认隐藏目录足以让健康分直接触底，但“存在一个 30 天未修改、没有匹配到已安装应用的目录”并不等于系统不健康。

影响：

- 用户会认为 Memento 用夸大的红灯制造清理焦虑。
- 真正重要的高 CPU 服务、磁盘不足或终端错误被大量低置信线索淹没。
- Agent 的“需要证据”原则与首页评分逻辑发生冲突。

#### P0：首次入口依赖模型，但模型并不是开箱即用能力

应用默认打开 Agent 页面，快捷任务在未配置 Provider 时被禁用；与此同时，确定性扫描会在后台自动执行约 9 秒。用户第一次看到的是一个核心动作不可用的页面，而真正无需 AI 的体检结果藏在第二个导航项。

#### P0：安全清理缺少非 AI 批量闭环

现在用户可以逐条直接操作，或让 Agent 生成计划，但没有一个面向普通用户的“选择安全项 -> 查看精确影响 -> 一次确认 -> 执行 -> 验证 -> 历史”的标准流程。AI 不应是批量清理的唯一编排器。

#### P0：操作历史不完整

任务记录主要围绕 Agent Run 和 Tool Call。直接存储清理、磁盘移到废纸篓、应用卸载和服务操作也应进入统一操作账本，否则最需要审计的动作反而散落在会话之外。

#### P1：应用管理不等于完整卸载

应用页主要把 `.app` 本体移到废纸篓；用户对“卸载”的预期通常还包括精确 Bundle ID 对应的启动项、Helper、偏好、缓存和残留。服务页已有部分精确关联能力，但没有汇总成一个一致的卸载预览。

#### P1：候选项信噪比过低

78 个待确认隐藏目录同时出现，超过普通用户的审阅能力。它们需要单独归入“线索”而非“建议”，按证据、空间价值和最近活动排序，并默认折叠低置信项目。

#### P1：扫描体验缺少缓存和首屏分层

整机体检约 9 秒尚可接受，但当前磁盘浏览通过 `/usr/bin/du -akx` 扫描整个数据卷，没有持久缓存。大磁盘、隐私拒绝和重复进入时的等待会更加明显。

#### P1：核心文件继续膨胀

- `src/main/scanner.ts` 约 2,349 行。
- `src/main/index.ts` 约 1,461 行。
- `src/renderer/src/App.tsx` 约 1,495 行。
- `src/main/agent/local-agent-runtime.ts` 约 763 行。

这些文件同时承担扫描策略、IPC、状态协调和 UI 工作流。继续加入卸载、批量计划和历史功能前，应按所有权拆分，而不是做无目标重构。

#### P1：公开发行范围与产品能力不一致

README 明确 Windows/Linux 仅用于桌面壳可移植性验证，但 Release 仍发布 6 个非 macOS 安装包。它会制造支持预期，还让发布流程的大量复杂度服务于不可用功能。

#### P1：社区与反馈基础设施不足

仓库目前只有 Release 工作流，缺少 Issue 模板、贡献指南、安全报告入口、隐私脱敏诊断工具和规则提交流程。清理产品无法只靠开发者自己的机器成熟，必须把误报、漏报和 macOS 版本差异变成可安全回传的测试样本。

### 5.3 能力对照

| 维度 | Memento 当前 | Mole 当前 | 建议 |
| --- | --- | --- | --- |
| 首次价值 | 自动扫描，但默认页是未配置模型的 Agent | 安装后直接运行任务 | Memento 首次进入确定性体检摘要 |
| AI | 多供应商、本地证据、计划确认 | 无通用 AI 解释层 | 保持为差异化，但改成可选增强 |
| 安全执行 | 不透明 ID、快照、主进程复检 | dry-run、路径保护、日志、执行前检查 | 合并两者优点，增加统一预览与操作账本 |
| 清理规则 | AI/开发缓存、应用缓存日志、Homebrew、隐藏目录 | 覆盖面明显更广 | 先提高信噪比，再按真实回收价值扩展 |
| 批量清理 | 主要依赖 Agent 计划 | 原生命令预览和多选 | 增加无 AI 的统一选择托盘 |
| 应用卸载 | 应用本体为主，部分服务场景能带数据 | 完整残留预览较成熟 | 建立精确证据驱动的卸载清单 |
| 磁盘分析 | GUI 分栏、Ask AI、移到废纸篓 | Go TUI、缓存、Spotlight、JSON | 保留 GUI，补缓存、首屏和大文件索引 |
| 实时状态 | 仅扫描期指标与服务异常 | 完整实时状态 TUI | 暂不正面追赶，只保留可行动异常 |
| 系统优化 | 终端修复、少量服务/清理动作 | 21 类维护任务目录 | 不追求数量，仅做能复检的高价值动作 |
| 自动化 | 内部 typed IPC | JSON、NDJSON、CLI | 先提供脱敏诊断导出，后评估只读 CLI |
| 安装 | GitHub DMG + 自动更新 | Homebrew + curl | 增加 Homebrew Cask 和官网直接下载 |
| 平台 | 发布三平台，能力仅 macOS | 明确 macOS-first | 公开产品聚焦 macOS |
| 社区 | 尚未建立 | Issue/PR/安全/贡献闭环成熟 | 建立规则反馈与脱敏复现流程 |

## 6. 推荐的产品策略

### 6.1 目标用户

优先服务两类用户：

1. **不敢随便删文件的普通 Mac 用户。** 他们需要知道“是什么、为什么能删、会发生什么、能否恢复”。
2. **环境复杂的开发者和专业用户。** 他们有大量工具链缓存、后台服务、旧 SDK、终端配置和应用残留，需要证据关联而不是一键扫荡。

不建议在 1.0 前把目标扩大到硬件监控爱好者、风扇控制用户、跨平台桌面用户或企业设备管理。

### 6.2 核心产品承诺

建议所有页面和文档围绕四句话组织：

1. 扫描由本地确定性工具完成，不依赖 AI。
2. 每条建议都展示来源、证据、风险和预计空间。
3. Memento 只执行当前扫描注册、用户明确选择的操作。
4. 执行后复检；可恢复操作提供废纸篓或恢复入口。

### 6.3 产品范围排序

| 层级 | 应做 | 暂不做 |
| --- | --- | --- |
| 核心 | 可信清理、完整卸载、启动项、终端诊断、磁盘归属 | 通用 Shell Agent |
| 增长 | 安装包清理、项目构建产物、Homebrew Cask、脱敏诊断 | 全功能包管理器 |
| 差异化 | 本机证据关联、解释、计划、执行后验证 | 让模型猜测路径或命令 |
| 后置 | 与维护动作直接相关的性能信号 | iStat 式常驻监控、风扇控制、菜单栏 HUD |
| 后置 | 精确、可逆、可复检的系统修复 | 大而全的“系统优化”按钮 |

## 7. 优先级建议与验收标准

### P0-1：重做健康摘要和候选分层

把当前单一候选列表拆成三类：

| 层级 | 定义 | 默认行为 |
| --- | --- | --- |
| 可安全清理 | 精确允许列表、可重建、前置条件全部通过 | 计入可释放空间，可默认选中但仍需确认 |
| 建议处理 | 有明确本机证据的异常服务、重复应用、失效路径 | 计入待处理项，不默认执行 |
| 待确认线索 | 只有年龄、名称或缺失匹配等弱证据 | 不扣健康分，默认折叠，不默认选中 |

健康摘要改为三个独立指标：

- **系统状态：** 磁盘余量、持续高 CPU/内存、终端错误、启动失败等真实异常。
- **可释放空间：** 已验证安全操作的预计字节数。
- **待确认线索：** 需要用户或 Agent 进一步判断的数量。

验收标准：

- 78 个未确认隐藏目录不再让健康分降到 45。
- `risk=review` 且没有强本机证据的项目不进入健康分。
- 首页可以直接看到“安全可清理多少”和“另有多少线索”，两者不混算。
- 同一候选必须携带稳定的 `confidence`、`reasonCodes` 和 `evidenceLevel`，不能只靠展示文案反推分类。

### P0-2：让首次体验不依赖模型

首次启动流程建议改为：

```text
启动
  -> 立即显示本机摘要和扫描阶段
  -> fresh scan 完成后进入体检摘要
  -> 用户可无 AI 预览和处理确定性项目
  -> “让 Agent 解释”时才配置或选择模型
```

验收标准：

- 没有 Provider 时，首次打开不再落在一组被禁用的 Agent 快捷操作上。
- 扫描、筛选、批量选择、确认、执行和历史查看完全不依赖模型。
- AI 按钮清楚表达“解释/生成计划”的增量价值，而不是基础能力入口。
- 本机配置自动发现成功时可以低干扰提示，但不能阻塞首次扫描结果。

### P0-3：增加统一预览与批量执行

新增一个非 AI 的选择托盘或处理计划，统一承载存储、应用、服务和终端操作。每个操作展示：

- 名称、类别和精确影响范围。
- 预计释放空间及是否只是估算。
- 可恢复、永久删除或配置备份三种恢复级别。
- 是否需要管理员权限。
- 执行前会重新检查的条件。
- 未被默认选中的原因。

验收标准：

- 用户可以只选“可安全清理”并一次确认。
- 待确认线索和用户数据永不默认选中。
- 预览与真实执行使用同一组操作 ID 和同一组资格检查。
- 部分失败时逐项显示成功、失败、跳过和原因，不能把部分执行报告为整体成功。

### P0-4：建立统一操作账本

在现有 SQLite 中新增与 Agent 会话解耦的操作会话和操作项记录。Agent 计划、直接清理、磁盘删除、应用卸载、服务操作和终端修复全部写入同一账本。

建议记录：

- 操作 ID、扫描 ID、规则版本、开始/结束时间。
- 操作类型、风险、是否可恢复、预计与实际释放空间。
- 结果状态和稳定错误码。
- 废纸篓目标的可用恢复入口，或配置备份位置。
- 执行前检查与执行后验证摘要。

敏感路径可以只保存在本机账本；任何遥测或诊断导出默认使用归一化类别和哈希，不上传原始路径。

验收标准：

- 所有破坏性入口都能在历史中找到。
- 可恢复项提供“在废纸篓中显示”或对应恢复动作。
- 历史删除只删除审计记录，不触碰文件系统目标。

### P0-5：公开发行聚焦 macOS

建议停止在公开 Release 中提供 Windows/Linux 安装包，直到对应平台具备真实扫描和维护能力。可以保留内部 CI 的跨平台 Renderer 构建，用于类型和壳层可移植性检查。

验收标准：

- README、Release 和官网只把 macOS 标为可安装产品。
- Release 资产、更新清单和校验和只包含真实支持的 macOS 架构。
- Windows/Linux 可移植性构建转为不对用户发布的 CI Artifact。

### P1-1：完整卸载预览

把应用本体、精确 Bundle ID 残留、启动项、Helper、包收据和相关后台服务汇总到同一卸载对话框。

默认选择策略：

- 应用本体：默认选中并移到废纸篓。
- 精确匹配的可重建缓存：可默认选中，清楚标注。
- 启动项和已确认 Helper：默认选中，执行前检查同 Bundle ID 兄弟应用。
- 偏好、账号、会话、数据库和文稿：默认不选中。
- 只有厂商名、Team ID 前缀或模糊名称匹配的项目：不进入可执行计划。

验收标准：

- 每个路径都能解释由哪条本机证据关联。
- 应用仍运行、同身份副本存在或身份无法确认时关闭失败。
- 卸载前后都检查应用、启动项和目标状态。
- 至少建立 macOS 系统应用、嵌套 Helper、同 Bundle ID、多副本、符号链接和权限失败的回归夹具。

### P1-2：扩展两个高价值、低歧义场景

不要先复制 Mole 的全部缓存目录。优先扩展：

1. **安装包清理：** 仅扫描用户选择或明确允许的 Downloads、Desktop、Mail Downloads 和 Homebrew 缓存；识别 DMG、PKG、MPKG、ISO、XIP，ZIP 需要更严格分类。
2. **项目构建产物：** 只扫描用户配置的项目根目录，支持 `node_modules`、Rust `target`、Xcode DerivedData 等可重建产物；最近项目和活动工作区默认不选中。

每个新增规则必须提交：实机可回收字节、明确非目标列表、运行中保护、恢复级别和回归测试。不能以“看起来像缓存”作为上线依据。

### P1-3：分层扫描与性能预算

建议先测量，再决定是否引入原生 helper：

1. 为每个扫描模块记录耗时、超时、候选数和内存峰值，只保存在本机或以脱敏桶值上报。
2. 启动时先展示系统摘要和上次扫描结果，后台刷新；旧结果上的操作全部失效，直到新扫描重新注册。
3. 磁盘浏览缓存只用于展示和大小估算，执行前必须重新解析真实路径和类型。
4. 当 TypeScript + 系统工具无法满足性能目标时，再将目录遍历、硬链接去重和缓存下沉为签名、版本化的 Go/Rust helper。

建议性能目标：

| 指标 | 目标 |
| --- | ---: |
| 启动后出现可理解的本机摘要 | P95 < 1.5s |
| 常规健康 fresh scan | P95 < 10s |
| 磁盘浏览首批可交互结果 | P95 < 2s |
| 扫描取消响应 | P95 < 500ms |
| 执行操作的资格复检 | 单项 P95 < 1s，不含系统授权等待 |

### P1-4：建立安全反馈与社区流程

新增：

- `SECURITY.md`、`CONTRIBUTING.md`、Bug/误报/规则请求模板。
- “报告此建议”入口，生成用户可先审阅的脱敏诊断。
- 诊断内容包括规则 ID、macOS 版本、证据类型、错误码和路径类别；默认不含用户名、完整路径、应用清单、Prompt、API Key 或文件内容。
- 每个线上误报都转化为测试夹具或规则非目标。
- 对清理规则增加定期 macOS/应用 Bundle 漂移检查。

### P1-5：补齐分发入口

- 提供签名、公证的官网直接下载页。
- 条件成熟后提交 Homebrew Cask，降低安装与升级摩擦。
- README 首屏增加真实产品截图、3 个核心任务和安全承诺，不用发布工程细节占据主要篇幅。
- 建立中英文帮助页，解释完全磁盘访问、管理员权限、废纸篓、模型数据边界和卸载恢复。

### P2：只读自动化接口

先提供用户主动导出的脱敏诊断 JSON，再评估只读 CLI：

```text
memento diagnose --json
memento scan --json --category storage
memento history --json
```

初期不要提供执行命令。只有当鉴权、操作快照、确认语义和稳定 Schema 都成熟后，才考虑让 CLI 提交已注册操作 ID。

## 8. 技术架构优化建议

### 8.1 目标结构

```text
React Renderer
  +-- 首次体验 / 体检 / 应用 / 历史 / 设置
  +-- Finding ViewModel
  `-- Operation Cart
             |
             | typed IPC, no raw command
             v
Electron Main
  +-- ScanCoordinator
  |     +-- StorageScanner
  |     +-- ServiceScanner
  |     +-- ApplicationScanner
  |     `-- TerminalScanner
  +-- FindingPolicy
  +-- OperationRegistry
  +-- OperationExecutor
  +-- VerificationCoordinator
  +-- AuditStore
  `-- AgentAdapter
             |
             +-- optional signed native scan helper
             `-- user-configured model endpoint
```

### 8.2 Findings 合同

建议扩展当前 `ScanCandidate`，让分类依据成为数据而不是文案：

```ts
interface Finding {
  id: string
  scanId: string
  category: 'storage' | 'service' | 'application' | 'terminal'
  confidence: 'verified' | 'strong' | 'weak'
  risk: 'safe' | 'review' | 'blocked'
  reasonCodes: string[]
  evidence: FindingEvidence[]
  estimatedBytes: number | null
  estimateQuality: 'exact' | 'approximate' | 'unknown'
  operations: RegisteredOperationSummary[]
}
```

好处：

- 健康分、排序、默认选择和 Agent Context 使用同一事实。
- 可以稳定统计误报来自哪类 reason code。
- 文案和语言切换不会改变安全判断。
- 规则升级时可以通过 `ruleVersion` 解释历史行为。

### 8.3 统一操作执行器

当前不同操作分布在存储清理、应用废纸篓、服务清理、管理员移动和磁盘浏览路径中。建议所有操作最终进入一个 `OperationExecutor`：

```text
resolve opaque ID
  -> verify scan/session freshness
  -> evaluate operation preconditions
  -> resolve and fingerprint target
  -> enforce path/app/data policy
  -> acquire privilege boundary if required
  -> execute through Trash/permanent/config-backup adapter
  -> verify postconditions
  -> append immutable audit result
```

每种操作声明：

- `preconditions`
- `targetFingerprint`
- `recoveryMode`
- `privilegeMode`
- `execute`
- `verify`
- `stableErrorCodes`

Renderer 和模型只接触摘要，不接触真实 target payload。

### 8.4 按所有权拆分热点文件

建议在实现上述功能时顺势拆分：

| 当前文件 | 建议边界 |
| --- | --- |
| `src/main/scanner.ts` | `scan/coordinator.ts`、`scan/storage.ts`、`scan/services.ts`、`scan/applications.ts`、`scan/terminal.ts`、`findings/policy.ts` |
| `src/main/index.ts` | 按 `ipc/scan.ts`、`ipc/operations.ts`、`ipc/agent.ts`、`ipc/settings.ts` 注册 handler |
| `src/renderer/src/App.tsx` | `useScanWorkspace`、`useOperationCart`、`useAgentWorkspace`、`useUpdater` |
| `local-agent-runtime.ts` | Context、工具注册、计划校验、运行状态机分离 |

拆分原则是单一所有权和可独立测试，不追求文件小而进行机械拆分。

### 8.5 测试提升顺序

1. 路径规范化、符号链接、硬链接、大小写不敏感卷和可变父目录的性质测试/fuzz。
2. 同 Bundle ID、多副本、运行中 App、Helper 和系统应用卸载夹具。
3. 扫描到执行之间目标变化的 TOCTOU 测试。
4. 部分失败、权限取消、超时、进程状态未知的结果语义。
5. 缓存 Schema、过期、损坏、并发写和操作失效测试。
6. 使用临时 HOME 的端到端 fixture，禁止测试接触真实用户文件。
7. UI 继续保留四视口烟测，并增加首次无 Provider、108 个候选降噪和批量计划流程。

测试数量不是目标。目标是每个线上误报、漏报和危险边界都留下不可回退的合同。

## 9. 建议路线图

### `0.7`：信任重置

目标：用户第一次打开即可得到不夸大的本机价值。

- 健康、空间、线索三分法。
- 无 Provider 首次体验和确定性工作流。
- Finding 的置信度、reason code、估算质量字段。
- 所有直接操作进入统一账本。
- 扫描阶段耗时与稳定错误码。
- Security、贡献和误报模板。
- 公开发行范围收敛到 macOS。

发布门槛：在当前实机样本中，78 个弱证据目录不影响健康分；不配置模型也能完成一次安全清理并在历史中审计。

### `0.8`：清理与卸载闭环

目标：不依赖 Agent 也能完成可信的多项维护。

- Operation Cart、统一预览、批量确认、部分失败结果。
- 完整应用卸载预览。
- 安装包清理。
- 用户配置项目根目录下的构建产物清理。
- 统一 OperationExecutor 和更多安全边界测试。

发布门槛：预览和执行资格完全一致；用户数据永不默认选中；所有操作有复检和账本记录。

### `0.9`：性能、分发与反馈

目标：把可靠能力转化为可持续增长。

- 上次结果首屏、后台 fresh scan、磁盘缓存。
- 达不到性能目标时再引入签名原生 helper。
- Homebrew Cask、官网直接下载与帮助中心。
- 用户可审阅的脱敏诊断导出。
- 规则反馈进入自动化夹具。
- 可选、最小化的产品指标。

发布门槛：达到扫描性能预算；可从安装、首次扫描、预览到复检定位主要流失点，同时不收集敏感内容。

### `1.0`：稳定产品边界

目标：以可信维护 Agent 而非“大而全 Mac 工具箱”发布。

- 核心任务、权限说明、恢复语义和支持边界稳定。
- 操作 Schema 和历史迁移具备兼容策略。
- 至少覆盖两代 macOS 和 Intel/Apple Silicon 的真实设备验证。
- 误报率、操作失败率和扫描 P95 达到门槛。
- 再根据真实需求决定是否加入只读 CLI 或更多系统状态能力。

## 10. 指标体系

### 10.1 北极星指标

**每台活跃设备每周“执行成功且复检通过”的用户确认维护任务数。**

这个指标同时约束发现价值、用户信任、执行成功和验证能力，比“扫描出多少问题”或“模型调用次数”更健康。

### 10.2 漏斗指标

| 阶段 | 建议指标 |
| --- | --- |
| 安装 | DMG/Cask 安装来源、首次成功启动率 |
| 激活 | 首次扫描完成率、首次结果可见耗时 |
| 理解 | 预览打开率、证据展开率、Agent 解释使用率 |
| 信任 | 计划确认率、项目取消率、待确认线索忽略率 |
| 执行 | 成功/失败/跳过率、权限取消率、稳定错误码分布 |
| 结果 | 复检通过率、实际释放空间、恢复入口使用率 |
| 留存 | 7/30 日再次扫描和再次完成任务 |

### 10.3 安全与隐私护栏

任何可选遥测默认禁止收集：

- 原始路径、文件名、应用清单和目录内容。
- 用户 Prompt、模型响应和 API Key。
- Bundle ID 或服务名，除非用户在诊断预览中主动选择包含。
- 可反推个人身份的主机名、用户名和完整硬件标识。

若暂不引入遥测，也应先把同一指标保存在本机诊断页，让开发阶段能以用户主动导出的方式分析问题。

## 11. 风险与非目标

### 11.1 GPL 洁净室边界

Mole 使用 GPL-3.0，Memento 使用 MIT。可以研究产品行为、公开接口和安全思想，但不能复制 Mole 的实现代码、注释、规则数组、路径表或测试数据。建议执行：

1. 先把需求写成独立行为规格和非目标。
2. 由未复制源码的实现者依据 macOS 官方资料和实机测量重新实现。
3. 为来源不明确的规则保留设计记录。
4. Code Review 明确检查是否出现 Mole 特有文本、顺序或数据表。

### 11.2 清理范围膨胀

每个新增目标都会永久增加 macOS 版本、应用版本、权限和恢复测试。新增规则必须证明真实回收价值，并列出不会处理的用户数据。规则数、扫描候选数和“清理得更多”都不应成为 KPI。

### 11.3 AI 误导

模型可以解释已观察证据，但不能把常识推断升级为本机事实。只有确定性扫描器能注册操作；无证据的模型结论不改变置信度、健康分或默认选择。

### 11.4 缓存过期

扫描缓存只能提升展示速度，不能授权执行。任何来自旧扫描的操作 ID 必须失效，用户确认前应完成新快照和资格检查。

### 11.5 平台扩张

在 macOS 规则、安全、反馈和分发还未稳定前，不应投入 Windows/Linux 维护实现。平台数量不是早期竞争力。

## 12. 最终建议

Mole 最值得学习的不是某个缓存目录或 Go TUI，而是四件事：任务模型清楚、安全预览默认存在、真实问题快速沉淀为规则、分发与反馈形成闭环。

Memento 最值得保留的也不是“接入了多少模型”，而是确定性扫描、不透明操作 ID、用户确认、主进程复检和本机证据关联。下一阶段应把这些底层优势变成普通用户可以直接感受到的产品体验：**先看见可靠结果，再理解原因，然后选择操作，最后验证并能追溯。**

只要 `0.7` 先修正健康分、首次入口和操作审计，Memento 就能从“带 AI 的 Mac 清理器”转向更难被复制的“可信 Mac 维护 Agent”。
